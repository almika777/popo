# ADR-0003: Единый механизм редактирования записей при NoTracking

- Статус: Принят
- Дата: 2026-08-11

## Контекст

Frontend редактирует существующую запись по идентификатору. Запрос использует форму
`PUT /resource/{id}`: идентификатор передаётся в URL, новые значения — в теле запроса.

В `Popo.Storage` глобально установлен `QueryTrackingBehavior.NoTracking`. Поэтому запись,
полученная обычным запросом EF Core, не отслеживается. Изменение её свойств и вызов
`SaveChangesAsync` без дополнительного действия не изменяют БД.

## Решение

Для провайдеров, которые редактируют загруженную сущность, используется единый поток:

1. frontend сохраняет `id` выбранной записи;
2. frontend отправляет `PUT /resource/{id}` с изменяемыми значениями в JSON-теле;
3. backend загружает запись по `id`;
4. backend применяет значения из тела запроса;
5. backend явно подключает сущность к текущему DbContext и помечает её изменённой:

```csharp
dbContext.Attach(entity);
dbContext.Entry(entity).State = EntityState.Modified;
await dbContext.SaveChangesAsync(cancellationToken);
```

Допустимая альтернатива — `ExecuteUpdateAsync` с обязательным фильтром `Where(x => x.Id == id)`.
После сохранения маршрут обязан иметь явно зафиксированный контракт ответа. Снимок кеша и фонд денежного рынка
возвращают `200 OK` с сохранённой записью; сделки, оценки портфеля и денежные операции сейчас возвращают `204 NoContent`.
Для `204` интеграционная проверка должна перечитать запись из БД или через GET; один HTTP-статус не подтверждает,
что данные записаны в БД.

## Последствия

- все PUT-операции имеют одинаковую форму адресации и проверяемый контракт ответа;
- `NoTracking` не приводит к тихому пропуску сохранения;
- интеграционные тесты должны проверять запись после PUT, а не только HTTP-статус;
- при добавлении нового редактируемого ресурса нельзя использовать отсоединённую сущность с одним `SaveChangesAsync`.
