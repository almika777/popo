# ADR-0004: Обработка ошибок API вне контроллеров

- Статус: Принят
- Дата: 2026-10-08

## Контекст

Контроллеры одновременно вызывали application-сервисы и провайдеры, проверяли бизнес-условия,
перехватывали исключения и выбирали HTTP-статусы ошибок. Из-за этого правила обработки ошибок
дублировались, а поведение API зависело от конкретного endpoint.

## Решение

Контроллеры отвечают только за HTTP-маршрут, связывание входных данных, вызов application-сервиса
и формирование успешного HTTP-ответа. В контроллерах запрещены `try/catch`, проверки бизнес-ошибок
с возвратом `BadRequest`, `NotFound`, `Conflict` и другие способы преобразования ошибки в HTTP-ответ.

Application-сервисы выполняют бизнес-проверки и сигнализируют об ожидаемых отказах типизированными
исключениями из `Popo.Core.Common`:

- `InvalidApplicationRequestException` — запрос не может быть выполнен из-за его данных;
- `ApplicationResourceNotFoundException` — целевой ресурс отсутствует;
- `ApplicationConflictException` — операция конфликтует с текущим состоянием данных.

`ApiExceptionHandler` централизованно отображает эти типы в HTTP 400, 404 и 409 соответственно.
Неизвестные исключения логируются и возвращают общий HTTP 500 без раскрытия внутренних деталей.
Ошибки привязки модели и FluentValidation обрабатываются средствами MVC до вызова контроллера.
Провайдеры хранения не зависят от HTTP и не формируют HTTP-ответы.
`AddProblemDetails` регистрирует резервный ответ для `UseExceptionHandler`, если ни один
`IExceptionHandler` не обработал исключение.

## Последствия

- HTTP-контроллеры остаются тонкими и одинаково обрабатывают ошибки;
- проверки существования и конфликтов находятся в application-сервисах;
- ожидаемые ошибки сохраняют явные типы и единое отображение на HTTP-контракт;
- новые типы ожидаемых отказов должны быть добавлены в общий обработчик, а не в контроллеры;
- необработанные ошибки не маскируются под клиентские и остаются HTTP 500.
