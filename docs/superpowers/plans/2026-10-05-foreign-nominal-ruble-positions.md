# План отдельного расчёта позиций с валютным номиналом и рублёвыми торгами

> План исполнения и итоговый журнал реализации. Реализация, повторное ревью и проверки отражены ниже.

**Статус:** реализовано; остаются явно перечисленные ограничения оценочного результата.

**Goal:** показывать рублёвый финансовый результат открытой позиции относительно фактически уплаченной рублёвой себестоимости, включая изменение валютного курса.

**Architecture:** фабрика в Core выбирает калькулятор по валюте номинала и валюте торгов. Отдельный калькулятор обслуживает `FaceUnit = USD/EUR/CNY` и `CurrencyId = RUB/SUR`; калькулятор остальных позиций сохраняет существующие формулы. Application-сервис загружает исходные данные, а калькуляторы получают явный контекст без доступа к EF и HTTP.

**Tech Stack:** .NET 10, C#, EF Core/PostgreSQL, Next.js/TypeScript, MOEX ISS, курсы Банка России.

**Spec:** запрос пользователя от 05.10.2026; подтверждённый пример, выбранные правила расчёта и оставшиеся ограничения изложены ниже. Историческая сумма каждого опубликованного купона применяется только к своему периоду; текущий купон не переносится на весь срок владения.

## Границы

- Источник позиций — сделки; позиция остаётся вычисляемым агрегатом.
- Ключ позиции сохраняется: `SecId + BoardId + CurrencyId`.
- Новый путь выбирается по валютным полям с нормализацией регистра и `RUB/SUR`, без списка ISIN и названий эмитентов.
- Такая валютная пара описывает механику расчёта, но сама по себе не доказывает юридический статус замещающего выпуска. Калькулятор называется `ZoPositionCalculator` по прямому решению пользователя.
- Формулы остальных облигаций, фондов и рекомендаций в эту задачу не включаются. Изменение результатов выбранных позиций должно дойти до общих итогов через единый результат калькулятора.
- Портфельный график, TWR и сетевой адрес приложения находятся вне задачи.
- Тесты запрошены пользователем и прогнаны; сценарии и итог последнего прогона приведены ниже.
- Существующие комментарии, тесты и логи сохраняются. При необходимости миграций применяется ADR-0002: штатная генерация EF Core.

## Причина ошибки

1. `PortfolioPositionsService.CalculatePositionTradePricing` переводит историческую рублёвую цену покупки в процент валютного номинала по курсу на дату покупки.
2. Этот процент переводится обратно в рубли по текущему курсу и текущему номиналу.
3. `CalculatePositionIncome` передаёт полученную переоценённую цену в `PositionIncomeTrade.CleanPrice`, сохраняя фактическую цену только в `ActualCleanPrice`.
4. `PortfolioPositionCalculator.Calculate` выбирает фактическую себестоимость для P&L лишь при флаге индексируемого номинала. Для TCS этот флаг `false`, поэтому берётся переоценённая себестоимость.
5. Таблица показывает фактическую среднюю цену, но P&L рассчитан относительно другой базы. Пересчёт убирает валютную составляющую изменения стоимости из отображаемого рублёвого результата.

Пересчёт к текущему номиналу имеет отдельный смысл для амортизирующих выпусков; эта общая логика описана в `docs/modules/core.md`. В истории Git изменение `CalculateTradePricePercent` входит в `b5a144e` с заявленной целью применения исторического номинала. Рублёвый результат валютной позиции требует собственной политики себестоимости; исправление подписи или цвета таблицы причину не устраняет.

В той же цепочке неправильная база используется для `ApproximateTotalPnl`, его процента и годовой экстраполяции. Итоги страницы и портфеля суммируют уже полученные значения P&L.

## Предлагаемые правила расчёта

Для открытых партий без амортизации, при согласованном FIFO:

- `Q = Σ q_i`, где `q_i` — оставшееся количество в каждой партии.
- `C = Σ(q_i × P_i)`, где `P_i` — фактическая чистая цена покупки в рублях.
- `AverageBuyPrice = C / Q`.
- `MarketPriceRub = CurrentFaceValue × QuotePercent / 100 × RateToRub`.
- `MarketValueRub = Q × MarketPriceRub`.
- `UnrealizedPnlRub = MarketValueRub − C`.
- `UnrealizedPnlPercent = UnrealizedPnlRub / C × 100`.

Изменение курса входит в рублёвый P&L через текущую стоимость. Историческая рублёвая покупка остаётся неизменной; исторический валютный курс не нужен для её чистой себестоимости. Цена покупки в процентах номинала может быть справочным полем, но её отсутствие не должно блокировать чистый рублёвый результат.

«По чистой цене» исключает НКД, купоны, комиссии и налоги. Приблизительный общий результат открытого остатка добавляет опубликованные выплаты по открытым лотам, текущий НКД, вычитает НКД покупки и комиссию покупки. Он не является фактической выпиской брокера.

Для точного общего результата открытых партий без амортизации предлагается:

`ApproximateTotalPnl = CleanPnl + CurrentAccruedInterestOfOpenLots − PaidAccruedInterestOfOpenLots + PublishedCouponsAllocatedToOpenLots − BuyCommissionsOfOpenLots`.

Это результат до налогов и предполагаемой комиссии будущей продажи. НКД сделки хранится за одну бумагу, API ввода принимает НКД за весь объём — преобразование учитывается ровно один раз. Опубликованный график купонов не подтверждает фактическое зачисление денег брокером.

### Изменение купона во время владения

Требование пользователя: если 10 бумаг куплены при ставке 10%, а через полгода ставка стала 20%, исторический доход до изменения относится к ставке 10%, а последующий — к ставке 20%. Пересчёт всей истории по последней ставке запрещён.

Разделяются три самостоятельные величины:

1. **Уплаченный НКД** — фактическая сумма из покупки. Смена ставки и сегодняшнего курса её не изменяет. При частичной продаже к открытому остатку относится соответствующая доля этой суммы.
2. **Прошлые купоны** — отдельные опубликованные выплаты по своим датам, суммам и валютам. Фактические брокерские зачисления приложение не хранит; расчёт по MOEX является оценкой.
3. **Текущий НКД** — накопление только внутри текущего купонного периода на дату оценки. Используется согласованное значение MOEX в валюте расчётов либо расчёт по условиям именно этого периода; начисление не начинается заново с даты каждой покупки.

Для восстановления оценочного купонного результата требуется весь график, пересекающий владение: начало и конец каждого периода, опубликованная сумма купона, валюта, номинал и, при необходимости, ставка и базис расчёта дней. Приоритет имеет опубликованная сумма за конкретный период; ставка сама по себе недостаточна без номинала и условий начисления. Если ставка меняется внутри периода, необходимы соответствующие подынтервалы либо готовая сумма, уже учитывающая изменение.

`MoexCouponsEntity` хранит `StartDate`, `CouponDate`, `RecordDate`, `Value`, `ValueInRub`, `ValuePercent`, `FaceValue` и `FaceUnit`. Контракт `IPortfolioCouponProvider.GetPublishedHistoryAsync` возвращает все сохранённые купоны; фактических брокерских зачислений эти данные не заменяют.

MOEX публикует `RecordDate`, поэтому право покупки определяется датой фиксации владельцев; при отсутствии этой даты покупки внутри периода остаются неоднозначными. Пропуск ожидаемой даты по расписанию от `NextCouponDate` или разрыв периодов помечает результат неполным. Для купона используется опубликованный `ValueInRub`, если он есть, иначе сохранённый курс валюты на дату выплаты. Текущий НКД добавляется один раз, купленный НКД вычитается один раз. Формулу `текущий купон / текущий CouponPeriod × все дни владения` новый калькулятор не использует.

Для валютного номинала сумма выплаты из MOEX переводится в рубли по сохранённому курсу на дату выплаты; текущий НКД берётся из текущих данных MOEX в валюте расчётов. Условия выпуска могут задавать особую дату конвертации, которой в текущей модели нет, поэтому результат остаётся приблизительным.

Если часть исторических периодов, право на выплату или параметры текущего НКД восстановить нельзя, купонный/общий результат получает состояние неполноты. Последняя ставка не подставляется вместо отсутствующей истории. Годовой показатель использует тот же результат по периодам и наследует его полноту. Это требование относится к новому пути расчёта выбранных валютных позиций; расширение на остальные типы требует отдельного изменения границ задачи.

## Ограничения, оставшиеся вне реализации

| Вопрос | Найденное ограничение / предлагаемое решение |
|---|---|
| FIFO или средняя себестоимость | Реализация сохраняет существующее FIFO; средняя цена в таблице — взвешенная цена оставшихся партий, а не всех покупок. |
| Открытый или общий результат | Реализация считает только открытый остаток. Реализованный результат продаж и результат закрытых лотов не добавляются. |
| Порядок сделок внутри дня | PDF-парсер извлекал `TradeTime`, но прежнее хранилище его теряло; GUID не является временем исполнения. Время теперь сохраняется и передаётся калькулятору. Старые сделки без времени, где порядок меняет FIFO-себестоимость, помечаются неоднозначными, их P&L и общие итоги не публикуются. |
| История и фактические купоны | Реализация использует опубликованную историю сумм MOEX и помечает оценку неполной при пропущенных ожидаемых периодах или неоднозначном праве на выплату. Фактические брокерские зачисления и выписки не импортируются. |
| Валюта и дата купонных выплат | Исторические суммы конвертируются по сохранённому курсу даты выплаты. Отдельные условия выпуска, которые задают иную дату конвертации, пока не моделируются. |
| НКД | Купленный НКД вычитается из сделки, текущий НКД из MOEX добавляется один раз. Прошлые изменения купона учитываются только через опубликованные суммы периодов. |
| Комиссии и налоги | Фактическая комиссия покупки распределяется пропорционально оставшемуся количеству партии. Для налога пока нет привязки к конкретной позиции; предлагается результат до налогов с явной подписью. |
| Амортизация и корпоративные события | Основная формула выше относится к неизменному валютному номиналу. Для амортизирующей валютной бумаги нужно определить списание себестоимости погашенной части и учёт выплат, чтобы не учитывать их дважды. Обмен, списание или погашение также требуют источника событий. Без этих данных полный точный результат недоступен. |
| Бессрочность и изменение купона | Нельзя растягивать последний купон на годы, игнорируя изменение ставки, пропуски или отсрочки выплат. Для бессрочного выпуска не предполагается обязательное погашение через выдуманный срок. |
| Какая цена считается текущей | `CurrentPrice` выбирается из `LCurrentPrice`, `MarketPrice2`, `MarketPrice`, цен закрытия и `Last`; это оценка, которая может отличаться от цены немедленной продажи по bid. Предлагается сохранить источник оценки, возвращая его и время актуальности. |
| Дата курса и номинала | Сейчас курс привязан к дате `SysTime`; `SysTime` описывает время загрузки, а отдельные securities/marketdata кэшируются независимо. `SettleDate` и `FaceValueOnSettleDate` уже есть в модели. Нужно явно согласовать дату оценки, курс, номинал и НКД; нельзя соединять несовместимые снимки без указания этого. |
| Единицы курса | Применять курс за одну единицу валюты (`UnitRate = Value / Nominal`), а не исходное табличное значение за несколько единиц. `RUB/SUR` эквивалентны для классификации. |
| Отсутствующие данные | Сейчас `GetValueOrDefault()` в итогах превращает отсутствие оценки/P&L/курса в ноль. Нужен признак неполных итогов и список причин; «нет данных» не означает нулевой убыток или нулевую стоимость. |
| Закрытые партии и старые курсы | Проверка `canNormalizeOpenCost` требует данные всех покупок, включая уже проданные. В новом пути отсутствие курса закрытой покупки не должно блокировать известную рублёвую себестоимость открытого остатка. |
| Годовая доходность | Реализация сохраняет линейную экстраполяцию по открытым партиям; она не равна XIRR и чувствительна к недавним покупкам. При неполной купонной истории показатель скрывается. |
| Денежная точность | Сейчас контракты и БД используют `double`. Для нового калькулятора предлагается `decimal` внутри денежных формул и явное округление; это не восстанавливает утраченную точность входных данных. Полный переход хранения и API на `decimal` требует отдельного решения. |
| Детальная страница и агрегаты | Те же показатели используются на карточке позиции, в строке «Итого» и summary портфеля. Детальная страница выбирает позицию по `SecId + BoardId`, тогда как агрегат имеет ещё `CurrencyId`; совместимость ключа требуется проверить при реализации. |
| Исторические даты | `GetOverviewAsync(asOf)` сейчас вызывает загрузку позиций на `MoscowTime.Today`, хотя кеш рассчитывает на `asOf`. Это отдельное ограничение исторической сводки; нельзя заявлять её историческую точность после одного исправления нового калькулятора. |

НКД и порядок конвертации для валютного номинала регулируются условиями выпуска; пример биржевых правил пересчёта в рубли приведён в [методике MOEX, раздел 2.3](https://www.moex.com/files/43mmvs4t00f21twfsmh91x4hxv). Курс и количество единиц валюты публикуются отдельно в [таблице ЦБ](https://www.cbr.ru/currency_base/daily/).

## Проверенные сценарии

- TCS perp1 по текущему снимку после синхронизации: средняя `86 892,86 ₽`, рыночная цена `82 828,55 ₽`, стоимость `414 142,76 ₽`, чистый P&L **`−20 321,56 ₽`**; исторические купоны `+67 966,72 ₽`, приблизительный итог с купонами `+47 469,51 ₽`.
- Фабрика выбирает ЗО для USD/EUR/CNY с RUB/SUR, включая разный регистр; остальные проверенные пары остаются на `DefaultPositionCalculator`.
- Частичная продажа списывает первый FIFO-лот; цена и чистый результат остаются по открытому лоту.
- Разные суммы купонов и курсы на даты выплат считаются отдельно; выплата относится только к количеству, купленному до этой даты.
- Купоны до покупки и после даты оценки исключаются; текущий НКД прибавляется, уплаченный при покупке вычитается один раз.
- Покупка внутри купонного периода не считается заведомо имеющей право на выплату; неполная история без ожидаемых выплат скрывает приблизительный общий результат.
- Покрытие пустой истории до срока первой ожидаемой выплаты сохраняет полноту; разрыв между опубликованными периодами делает оценку неполной.
- Если последняя известная выплата была до покупки, её дата остаётся якорем графика: наступивший после покупки пропуск выплаты скрывает купонную оценку.
- До ожидаемой выплаты на 181-й день история ещё допустима; на границе 182-дневного периода без выплаты оценка уже неполная. Неизвестная частота при пустой истории не трактуется как бескупонность, явная частота 0 считается известной бескупонной бумагой.
- Отсутствующая историческая ставка помечает купонную оценку неполной; отсутствие текущего курса делает рыночную стоимость и P&L недоступными.

- Миграция `20261005140705_AddPositionTradeTimeAndCouponRecordDate` применена. После однократной синхронизации в базе 100 705 строк купонов, 98 256 с `RecordDate` и 58 278 с `ValueInRub`; по TCS сохранено 16 дат истории.

Границы реализации: история MOEX показывает опубликованные выплаты, а не фактические брокерские зачисления; если `RecordDate` отсутствует, право на выплату считается неполным; результат по уже закрытым FIFO-лотам не входит в показатели текущей открытой позиции; валютная амортизация, налоги и корпоративные события не моделируются.
