# План отдельного расчёта позиций флоатеров через TDD

> План исполнен по рекомендуемому первому этапу: рублёвые флоатеры, фактическая история купонов и линейная годовая оценка. Независимое ревью выявило три дефекта полноты/входных данных; добавлены падающие регрессионные сценарии, исправления и повторная проверка.

**Статус:** реализация, независимое ревью и автоматические проверки завершены. Ручная сверка конкретной бумаги требует выбранный флоатер и согласованный снимок портфеля. Применены ограничения RUB/SUR и историческая годовая экстраполяция.

**Goal:** выделить `FloaterPositionCalculator` и считать результат открытых партий по историческим суммам купонов, НКД покупки и текущему НКД, без распространения последнего купона на прошлые периоды.

**Architecture:** существующая фабрика выбирает ЗО по валютной паре, затем рублёвый флоатер по типу купона, затем стандартный калькулятор. Расчёты находятся в Core и получают готовые данные; API собирает котировку, сделки и купонный график. Общие операции FIFO и обработки истории выделяются из ЗО под защитой регрессионных тестов; правила себестоимости остаются ответственностью конкретного калькулятора.

**Tech Stack:** .NET 10, C#, NUnit 4, EF Core/PostgreSQL, Next.js/TypeScript, MOEX ISS.

**Spec:** запрос пользователя от 06.10.2026; правила, формулы и критерии приёмки зафиксированы в этом документе.

## Ограничения и выбранная семантика

- Первый этап: `FaceUnit` и `CurrencyId` равны RUB/SUR. Остальные валюты требуют отдельного определения валюты исторических выплат и НКД; это вопрос пользователю, а не неявное обещание поддержки.
- ЗО с плавающим купоном сохраняет валютную себестоимость и выбор `ZoPositionCalculator`. Валютная механика и тип купона — независимые признаки; приоритет фабрики фиксируется тестом.
- Оценивается открытый FIFO-остаток. Прибыль проданных партий, купоны проданной части и комиссии продажи не входят в показатели текущей позиции.
- Рыночная стоимость и чистый P&L не включают НКД и комиссии. Купонный результат включает опубликованные выплаты по открытым партиям, текущий НКД и вычитает НКД покупки. Общий результат дополнительно вычитает комиссию покупки открытой части.
- Для сравнимости со старым контрактом процент результата и годовая оценка используют чистую себестоимость, принятую для чистого P&L. Это явно заданная база показателя, а не доходность на весь денежный расход с НКД и комиссиями.
- Годовая оценка остаётся линейной экстраполяцией исторического результата каждой открытой партии. Сценарий будущей ключевой ставки/RUONIA, прогноз купонов и YTM — другие расчёты.
- НКД берётся из сделки и биржевого снимка. Универсальный пересчёт НКД по текущей ставке, `CouponValue` или длительности владения не применяется.
- Опубликованная сумма MOEX означает оценку договорной выплаты, а не подтверждённое зачисление брокером. Налоги, дефолты и фактические зачисления не восстанавливаются из купонного графика.
- Нормализация чистой себестоимости к текущему номиналу сохраняет существующую семантику стандартных бумаг. Амортизационные выплаты не добавляются в результат этой задачи; UI должен сохранить соответствующую оговорку.
- Core не получает EF/HTTP. Controllers остаются HTTP-слоем. Существующие комментарии, тесты и логи сохраняются.
- Запуск приложений и остановленных процессов не является частью задачи. Полный прогон Storage-тестов требует доступного Docker; одна общая PostgreSQL-база и изоляция по ADR-0001.

## Что подтверждено в текущем коде

1. `PositionCalculatorFactory.Create(faceUnit, currencyId)` знает только ЗО и стандартный путь.
2. `DefaultPositionCalculator` вызывает `PortfolioPositionCalculator.Calculate`: купоны считаются как `последний купон / CouponPeriod × дни владения`. `PositionIncomeTrade.AccruedInterest` в этой формуле не участвует.
3. `ZoPositionCalculator` уже строит открытые FIFO-партии, учитывает НКД/комиссию, исторические суммы, `RecordDate`, `ValueInRub`, время исполнения и неоднозначность порядка. Нельзя копировать его рублёвую конвертацию для любых валют.
4. `BondSecurityDto.IsFloater` распознаёт `флоатер` либо сочетание `плавающ` и `купон` в `BondType`/`BondSubType`. Источник позиций — `MoexBond`, у которого эти поля есть, но общего классификатора нет.
5. `IPortfolioCouponProvider.GetPublishedHistoryAsync` возвращает только строки с `CouponDate <= asOf`. Ближайший будущий период не попадает в результат; неполную историю нельзя надёжно проверять только по текущему `CouponPeriod`.
6. Текущие модели MOEX и `PositionCalculationInput` представляют текущий НКД как `double`. Отсутствие значения нельзя явно передать калькулятору как `null`.
7. В журнале есть дата и время сделки, но нет даты расчётов сделки. `MoexBond.SettleDate` не является исторической датой расчётов каждой покупки.
8. Сервис фильтрует купонные выплаты по дате котировки, но передаёт калькулятору календарное `asOf`. Для флоатера нужно явно определить согласованную дату оценки НКД, выплат и годового результата.
9. В `CreateValuedPosition` купонный и общий результаты дополнительно зависят от `couponValue.HasValue`. Новый расчёт по известной истории не должен блокироваться отсутствием последнего купона.

Правила НКД различаются по условиям выпуска и виду ставки. Методика MOEX содержит отдельные правила для плавающих купонов и ОФЗ-ПК: [методика, действует с 22.06.2026, разделы 2.1, 2.2, 2.4](https://www.moex.com/files/4pmhxzvda2tkqs08jcb19jmedh). Поэтому текущий опубликованный НКД применяется как входное значение, а собственная модель ставки в эту задачу не включается.

## Формулы

Для каждой оставшейся партии `i`:

```text
q_i       = оставшееся количество после FIFO-продаж
B_i       = q_i × чистая цена покупки, принятая для ценового P&L
C_i       = сумма положенных опубликованных купонов на q_i
            + q_i × текущий НКД
            − q_i × НКД покупки
F_i       = комиссия покупки × q_i / исходное количество покупки
P_i       = q_i × текущая чистая цена − B_i
R_i       = P_i + C_i − F_i

Чистый результат = ΣP_i
Купонный результат = ΣC_i
Общий результат = ΣR_i
Общий результат, % = 100 × ΣR_i / ΣB_i
Годовая оценка, % = 100 × Σ(R_i × 365 / max(1, дни владения_i)) / ΣB_i
```

При неполных купонных данных чистая цена, стоимость и чистый результат остаются доступными, если достаточно данных для себестоимости. Купонный, общий и годовой результаты возвращаются клиенту как `null`, а не как ноль или сумма известных фрагментов.

## Данные, полнота и право на выплату

- Для флоатера загрузить сохранённый график с началом/концом каждого периода, `RecordDate`, `Value`, `ValueInRub`, включая ещё не наступившие периоды. В сумму включать только положенные выплаты с датой не позже даты оценки.
- Добавить к существующему `IPortfolioCouponProvider` метод `GetCouponScheduleAsync(IReadOnlyCollection<PortfolioBondKey> bonds, CancellationToken cancellationToken)`, возвращающий `IReadOnlyList<PublishedCouponValue>` без фильтра по дате. Старый `GetPublishedHistoryAsync` сохранить для совместимости.
- Верифицировать покрытие интервала владения по фактическим границам периодов. Нельзя восстанавливать весь график шагом назад по последнему `CouponPeriod`: длительность купонов и даты выплат меняются.
- Нулевая опубликованная выплата допустима. Неизвестная сумма прошедшей положенной выплаты означает неполноту; неизвестная сумма будущего купона не блокирует уже известный исторический результат.
- Пустая история допустима до первой положенной выплаты только при наличии графика, который это подтверждает. Пустая история сама по себе не означает нулевой доход.
- Сумму выбирать в рублях: валидная `ValueInRub`, иначе валидная `Value` для RUB/SUR. Для флоатера вне выбранного валютного охвата эти правила не применять.
- Отсутствие НКД, отрицательные/NaN/Infinity значения, конфликтующие дубли и разрывы графика не заменять нулём. Идентичные дубли одной выплаты не суммировать повторно.
- Для ЗО сохранить существующую политику определения права на купон при извлечении общего кода. Для нового флоатера при недоказанном праве на выплату возвращать неполный результат.
- Для старых сделок без даты расчётов покупка внутри купонного периода возле фиксации владельцев не доказывает право на купон. В первом этапе неоднозначный результат скрывать; поддержка точной `SettlementDate` в журнале/импорте потребует отдельного расширения. Не угадывать расчёты через `AddDays(1)`.
- Для флоатера использовать явную дату оценки купонного результата и доступный снимок НКД. Если данные относятся к несовместимым датам или котировка предшествует открытой покупке, общий/годовой результат скрывать. `SysTime` не доказывает актуальность каждого поля securities; это отдельное условие согласованности данных.

## Критерии приёмки и границы текущего этапа

- Числа C1/C3/C5/C7 совпадают с независимыми формулами; изменение текущего купона не меняет исторические выплаты.
- Фабрика выбирает правильный путь; проверенные результаты ЗО и нефлоатеров сохраняются.
- Недостаточные данные не превращаются в положительный/нулевой доход. Чистый результат доступен независимо от полноты купонной истории.
- Даты, валюта и единицы НКД/купона согласованы; купон не начисляется дважды и не достаётся повторно открытой позиции за прошлое владение.
- API и UI показывают именно рассчитанный результат, включая отрицательные значения и `null`; отчёт исполнения указывает ограничения и результаты реально проведённых проверок.

Выполнен рекомендуемый первый этап RUB/SUR с исторической линейной годовой оценкой; валютные флоатеры и прогноз будущей ставки не входят в эту реализацию. Для точных пограничных прав на купон при T+расчётах требуется сохранять `SettlementDate` сделки, а для полного общего P&L — учитывать фактические амортизации и подтверждённые брокером выплаты. Эти расширения не подменяются предположениями в текущем калькуляторе.
