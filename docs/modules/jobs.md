# Popo.Jobs

Отдельное приложение для Hangfire: регистрирует Core, HTTP-клиенты, Storage и джобы,
обслуживает очереди `fast` и `long` одним worker-ом на очередь.
Все зависимости регистрируются до `builder.Build()`.

## Расписание

Восемь синхронизаций запускаются ежедневно в 09:00 по Москве:

- `long`: описание облигаций, торговые режимы, история, купоны/амортизации, курсы ЦБ;
- `fast`: SEC, эмитенты, рейтинги.

Мониторинг открытых позиций запускается каждые 15 минут в `fast`.
Расчёт кандидатов по кешу остаётся ручным запросом к API.

## Запуск

Jobs использует ту же `ConnectionStrings:DefaultConnection`, что и API.
Миграции применяет `Popo.Api`; Jobs самостоятельно схему приложения не обновляет.
В Docker Compose PostgreSQL сначала проходит healthcheck, затем `jobs` ждёт `service_healthy` backend-а: API начинает
обслуживать `/health` после завершения миграций. Это условие порядка запуска,
а не постоянный контроль доступности базы.
Healthcheck выполняет `dotnet Popo.Api.dll --healthcheck`: отдельный короткий процесс
проверяет HTTP `/health` на порту 8080 и завершается с кодом 0 или 1, не создавая host
и не применяя миграции повторно.

Для запуска без Docker сначала нужно дождаться готовности API, затем запустить
`dotnet run --project src/Popo.Jobs/Popo.Jobs.csproj --urls http://localhost:5110`.

В Docker Dashboard доступен по `http://localhost:5110/hangfire`; опубликованный порт
привязан к `127.0.0.1`. Фильтр приложения допускает loopback и приватные адреса Docker/LAN.
`GET /health` Jobs подтверждает доступность HTTP host-а, но не успешность синхронизаций.

После завершения записи истории `MoexHistoryPricesUpdateJob` вызывает
`DailyVolumeStatisticsStore.RefreshAsync`. При частичных ошибках получения бумаг
снимок строится по сохранённой истории; дата актуальности хранится отдельно для каждой бумаги.
При ошибке writer-а пересчёт не запускается. Правила снимка описаны в [Storage](storage.md).
